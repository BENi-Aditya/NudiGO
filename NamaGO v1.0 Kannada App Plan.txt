Product Name:
NamaGO

Working tagline:

Core product statement:
NamaGO is a mobile-first, gamified Kannada-learning app designed for people who
have recently moved to Bangalore or otherwise want to communicate comfortably
in Kannada. It combines a guided, Duolingo-inspired learning path with
contextual lessons, speaking practice, AI conversations, spaced review, and
real-world missions.

Design system:
Playful Minimalism + Kinetic UI

Primary audience:
- Students moving to Bangalore
- Young professionals moving to Bangalore
- Migrants from other Indian states
- English/Hindi speakers beginning Kannada
- Visitors who want practical Kannada
- Existing Bangalore residents who want to improve spoken Kannada

Initial product scope:
- Kannada for English-speaking beginners
- English UI
- Kannada script + Roman transliteration + English meaning
- Bangalore-first practical situations
- Mobile-first web app / installable PWA if time permits

Important positioning:
NamaGO is NOT "a Kannada dictionary."
NamaGO is NOT "Google Translate with gamification."
NamaGO is NOT a generic AI chatbot.
NamaGO is a guided learning system whose AI is used for practice and adaptation.

================================================================================
1. EXECUTIVE SUMMARY
================================================================================

Problem:
People who move to Bangalore often want to learn Kannada but struggle to find a
modern, structured, motivating, beginner-friendly learning experience focused on
the Kannada they actually need in daily life. Traditional resources can be
text-heavy, fragmented, or disconnected from real-world situations.

Agitation:
A newcomer can memorize vocabulary and still freeze when an auto driver asks
a simple question, a shopkeeper responds in Kannada, or a restaurant worker
asks a follow-up. The problem is not simply lack of vocabulary. It is lack of
retrieval practice, context, listening, speaking confidence, and repeated use.

Solution:
NamaGO turns practical Bangalore situations into short interactive lessons.
A learner sees a phrase, hears it, understands it, practices it through varied
exercises, speaks it, uses it in an AI roleplay, and receives a real-world
mission. Previously learned concepts return through spaced review and new
contexts.

The core loop:
Learn -> Practice -> Speak -> Simulate -> Use in real life -> Return -> Review

Hackathon thesis:
Do not build a massive language platform. Build one polished, convincing
learning journey that demonstrates that a complete beginner can learn and use
useful Kannada within minutes.

================================================================================
2. PRODUCT VISION
================================================================================

Vision:
Make learning an Indian regional language feel as intuitive, rewarding, and
socially normal as learning a global language on a modern consumer app.

Long-term vision:
NamaGO becomes a language-learning engine for Indian regional languages,
starting with Kannada and expanding to Tamil, Telugu, Marathi, Bengali,
Malayalam, Gujarati, Punjabi, and others.

Near-term vision:
Become the easiest way for a newcomer to Bangalore to become conversationally
useful in Kannada.

Product promise:
"You don't need to become fluent today. You just need to know what to say next."

================================================================================
3. PRODUCT PRINCIPLES
================================================================================

3.1 Practical before theoretical
Teach phrases that solve real problems before teaching abstract grammar.

3.2 Context before vocabulary lists
Words are introduced inside situations and reused in different contexts.

3.3 Guided, not overwhelming
The app always provides one clear next action.

3.4 Small lessons, meaningful progress
A lesson should generally take 3–7 minutes.

3.5 Retrieval over passive reading
Users should repeatedly recall, select, build, hear, and say language.

3.6 Speak early
Speaking should appear in beginner lessons, even when imperfect.

3.7 AI assists; curriculum controls
AI provides roleplay, feedback, hints, and adaptation. It must not invent the
core curriculum or become the sole authority for Kannada correctness.

3.8 Real-world transfer
The ultimate success metric is not XP. It is whether the learner can use the
language outside the app.

3.9 Reward progress, not perfection
Mistakes are expected. Feedback should be encouraging and specific.

3.10 Visual simplicity
Each screen has one primary task. Avoid dense dashboards and generic SaaS UI.

3.11 Motion has purpose
Animation communicates state, feedback, progress, hierarchy, or delight.
Never animate merely because animation is available.

3.12 Kannada is a first-class visual language
Kannada script should be large, legible, and treated as primary content.

================================================================================
12. LEARNING SCIENCE / CURRICULUM MODEL
================================================================================

NamaGO uses a simplified retrieval-and-review model.

Each concept has:
- Concept ID
- Kannada form
- Transliteration
- English meaning
- Audio
- Skill
- Difficulty
- Related concepts
- Example phrases
- Common mistakes
- Review status

Concept mastery states:
0 = unseen
1 = introduced
2 = practiced
3 = recalled
4 = used in context
5 = strong

A concept should appear across multiple contexts.

Example:
beku = want/need

Lesson 6:
Coffee beku.

Lesson 8:
Nanage neeru beku.

Lesson 11:
Nanage auto beku.

Lesson 15:
Help beku.

The exact curriculum must be reviewed by a competent Kannada speaker before
production use.

Review scheduling:
- Immediate reappearance within the lesson
- Short-delay review in a later lesson
- Contextual review several lessons later
- User-triggered review when errors occur
- Optional daily review queue

Do not use a simplistic "learn once = mastered" model.

15. SPEAKING SYSTEM
================================================================================

Goal:
Make speaking feel approachable, not like an exam.

Flow:
Prompt
  ->
Tap microphone
  ->
Record
  ->
Speech-to-text
  ->
Normalize text
  ->
Compare with expected intent / phrase
  ->
Generate feedback
  ->
Continue or retry

Hackathon implementation:
Prioritize functional speech-to-text and reasonable phrase matching.
Do not attempt scientifically precise phoneme scoring unless time permits.

Feedback categories:
- Meaning correct
- Close
- Try again
- Pronunciation hint
- Word missing
- Extra word

Example:
Expected:
Ondu coffee kodi.

User transcript:
Ondu coffee.

Feedback:
"Almost! Add 'kodi' at the end."

Avoid numeric scores unless they are meaningful and defensible.

16. AI CONVERSATION SYSTEM
================================================================================

Purpose:
Provide safe, constrained conversational practice.

AI roles:
- Waiter
- Auto driver
- Shopkeeper
- Classmate
- Friend
- Receptionist
- Local resident

Scenario object:
- scenario_id
- title
- context
- role
- learner_level
- target_concepts
- opening_message
- allowed_complexity
- success_condition

System prompt requirements:
- Speak appropriate Kannada for learner level.
- Provide transliteration when configured.
- Do not introduce unexplained advanced grammar unless intentionally teaching it.
- Stay inside the scenario.
- Be patient.
- Correct meaningful mistakes.
- Prefer short responses for beginners.
- Never pretend that generated language is authoritative without curriculum grounding.
- If uncertain about a Kannada phrase, fall back to approved curriculum phrases.

Conversation states:
1. Start
2. User response
3. AI response
4. Feedback/hint if needed
5. Continue
6. Success/failure
7. Summary

AI should not be responsible for:
- Authentication
- XP calculations
- unlocking lessons
- permanent progress decisions
- security rules

Those belong to application logic.

20. DESIGN SYSTEM
================================================================================

Design direction:
PLAYFUL MINIMALISM + KINETIC UI

Design goals:
- clean
- friendly
- modern
- youthful
- tactile
- expressive
- accessible
- fast

Avoid:
- generic SaaS dashboard aesthetics
- excessive glassmorphism
- excessive gradients
- card overload
- tiny typography
- huge decorative hero sections inside lessons
- unnecessary animations
- visually noisy backgrounds

Core principle:
One screen = one primary cognitive task.

Color system:
Use a small tokenized palette.
Recommended direction:
- Primary: Karnataka-inspired deep green
- Accent: warm yellow
- Secondary accent: terracotta/coral
- Background: warm off-white
- Text: deep charcoal
- Success: accessible green
- Error: accessible red
- Neutral surfaces: warm gray

Exact hex values should be finalized during visual prototyping and checked for
contrast.

Typography:
Primary recommendation:
Nunito or a similarly friendly rounded sans-serif.
Use a Kannada-capable font for script rendering where needed.
Kannada content must remain highly legible.

Type scale:
Display: 40–48 px
H1: 32–40 px
H2: 24–32 px
Body: 16–18 px
Secondary: 14–16 px
Caption: 12–14 px

Kannada lesson text:
Prefer larger size than surrounding explanatory text.

Spacing:
Use a consistent spacing scale, e.g.
4 / 8 / 12 / 16 / 24 / 32 / 48 / 64.

Radius:
- Buttons: 12–16 px
- Cards: 16–20 px
- Pills: 999 px
Avoid random radius values.

Shadows:
Soft, limited shadows.
Prefer hierarchy through spacing and contrast.
Use tactile shadow for primary buttons where appropriate.

27. APPLICATION LOGIC
================================================================================

Lesson unlock:
Lesson N unlocks when prerequisite requirements are met.

XP:
Server should validate important rewards to prevent trivial client manipulation.

Progress:
Persist after meaningful events, not every animation frame.

Review:
When a learner gets an exercise wrong, related concepts receive higher review
priority.

AI:
AI output does not directly unlock content unless server logic confirms the
required condition.

Conversation success:
Can be based on completion of scenario objectives rather than exact wording.

37. VIBECODING RULES
================================================================================

Rule 1:
Never ask the coding agent to build the whole product in one prompt.

Rule 2:
Implement one vertical slice at a time.

Rule 3:
After every feature:
- run app
- test manually
- fix errors
- commit

Rule 4:
Do not allow generated code to silently replace working architecture.

Rule 5:
Keep business logic separate from UI.

Rule 6:
Keep curriculum in structured data, not scattered inside components.

Rule 7:
Use reusable exercise components.

Rule 8:
Use design tokens instead of random CSS values.

Rule 9:
Do not add a dependency unless it solves a real problem.

Rule 10:
If a feature is not required for the demo, defer it.

Recommended development rhythm:

Prompt agent
  ->
Run app
  ->
Test
  ->
Screenshot/error
  ->
Ask agent to fix
  ->
Commit
  ->
Next feature

45. RISKS AND MITIGATIONS
================================================================================

Risk:
Incorrect Kannada generated by AI.
Mitigation:
Human-verified curriculum and constrained AI scenarios.

Risk:
Too much scope.
Mitigation:
Vertical slice and strict MVP.

Risk:
App looks like generic VibeCode.
Mitigation:
Design system before feature expansion.

Risk:
Speaking feature is unreliable.
Mitigation:
Use speech-to-text + phrase/intent matching for MVP.

Risk:
Gamification overwhelms learning.
Mitigation:
Keep learning task primary.

Risk:
User learns phrases but doesn't use them.
Mitigation:
Real-world missions.

Risk:
Users abandon onboarding.
Mitigation:
Minimal onboarding and immediate first lesson.

Risk:
Content feels textbook-like.
Mitigation:
Bangalore-first scenarios and spoken language review.
